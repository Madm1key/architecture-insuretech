# Task 3. Анализ текущей архитектуры InsureTech

## Проблемы и риски при текущей архитектуре

### 1. Синхронный опрос страховых компаний

`ins-product-aggregator` при каждом запросе синхронно опрашивает все 5 страховых компаний.
Плаинруется расширение до 10.

- Суммарное время ответа вырастет пропорционально количеству партнёров.
- Один медленный или недоступный партнёр блокирует ответ агрегатора для всех потребителей.
- Вероятность хотя бы одного сбоя при запросе 10 API одновременно растёт экспоненциально.
- **Риск:** недоступность одной страховой компании приводит к деградации `core-app` и
  `ins-comp-settlement`.

### 2. Polling тарифов каждые 15 минут

`core-app` запрашивает тарифы у `ins-product-aggregator` по расписанию раз в 15 минут:

- Каждый цикл порождает N синхронных вызовов во внешние API (N = кол-во страховых компаний).
- При пиковой нагрузке 50 RPS на 100% поиск эти фоновые запросы конкурируют за ресурсы.
- Если `ins-product-aggregator` недоступен в момент polling — данные устаревают, повторная попытка
  не предусмотрена.
- **Риск:** с ростом числа партнёров нагрузка на `ins-product-aggregator` и внешние API растёт
  линейно.

### 3. Дневной batch-запрос `ins-comp-settlement` к `core-app`

`ins-comp-settlement` раз в сутки забирает весь список оформленных страховок через REST:

- Объём данных растёт с ростом клиентской базы — один большой запрос создаёт пиковую нагрузку на
  `core-app`.
- При недоступности `core-app` в момент запроса взаиморасчёты за сутки срываются.
- Нет механизма частичной перекачки: если запрос упал на полуслове — нужен полный повтор.
- **Риск:** по мере роста объёма страховок запрос будет занимать всё больше времени и ресурсов
  `core-app`.

### 4. Отсутствие буферизации между сервисами — жёсткая связность

Все взаимодействия между внутренними сервисами синхронные (REST pull):

- Перезапуск или деградация любого сервиса немедленно видна потребителям.
- Невозможно независимо масштабировать производителей и потребителей данных.
- Горизонтальное масштабирование `ins-product-aggregator` не снижает нагрузку на внешние API
  страховых компаний.
- **Риск:** при плановом масштабировании любой внутренний сбой каскадно распространяется
  на всю цепочку.

### 5. Нет гарантии доставки при оформлении страховок

При оформлении страховки `core-app` записывает данные в БД и должен уведомить `ins-comp-settlement`
для будущих взаиморасчётов. В текущей модели (pull раз в сутки) нет механизма, гарантирующего, что
запись попадёт в реестр:

- Если страховка оформлена, но при дневном запросе произошёл сбой — данные теряются до следующего
  цикла.
- **Риск:** финансовые потери из-за пропущенных взаиморасчётов.

## Transactional Outbox с Transaction Log Tailing (Debezium)

Для решения проблемы #5 будет применен паттерн **Transactional Outbox** в связке с **CDC (Change
Data Capture)** через Debezium.
